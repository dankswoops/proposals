NIP-XX
======

Kin
---

`draft` `optional` `kind:10094` `replaceable`

## Abstract

A replaceable event listing the people a user counts as family, each with a code
for the relation and an optional mark for its gendered form.

Every entry is the author's own claim about their own family. It is not a
genealogy, not a social graph, and not a substitute for following.

## Event

```json
{
  "kind": 10094,
  "content": "",
  "tags": [
    ["kin", "3b7fc823...", "", "1", "2"],
    ["kin", "a1c9e40d...", "wss://relay.example.com", "1", "1"],
    ["kin", "f0e2b118...", "", "3", "2"],
    ["kin", "77c3a5e9...", "wss://relay.example.com", "2", "1"]
  ]
}
```

That reads: my mother, my father, my sister, my son.

* `kin` — repeatable: `["kin", "<pubkey>", "<relay-url>", "<relation>", "<sex>"]`
  * the relay hint may be an empty string, as [NIP-10](../nips/10.md) does for
    marked `e` tags
  * the relation is a code from the table below
  * the sex is `1` or `2`, or the element is left off entirely

`content` is unused. Skip any `kin` tag whose relation is missing, non-integer or
unrecognised, and keep the rest of the list — that is what lets the vocabulary
grow without breaking older readers. Ignore a sex that is neither `1` nor `2` and
treat the entry as unspecified rather than dropping it.

Relations read outward from the author: `["kin", X, "", "1", "2"]` means *X is my
mother*, never *I am X's mother*.

The second element names a person, so it is a 64-character lowercase hex pubkey;
skip any tag where it is not, since there is nobody to look up. The author's own
pubkey does not belong here either — ignore it if it appears.

### Withdrawing

The list is full state, not a set of edits: each event replaces the last, so
removing one person means republishing everyone else. To clear it entirely,
publish an event carrying nothing:

```json
{
  "kind": 10094,
  "content": "",
  "tags": []
}
```

A [NIP-09](../nips/09.md) request may go alongside, but it only reaches relays
that receive it, whereas the replacement travels the same path the original did.

## Relations

| Code | Relation |
|------|----------|
| `0` | relative |
| `1` | parent |
| `2` | child |
| `3` | sibling |
| `4` | half-sibling |
| `5` | grandparent |
| `6` | grandchild |
| `7` | aunt or uncle |
| `8` | niece or nephew |
| `9` | cousin |
| `10` | parent-in-law |
| `11` | child-in-law |
| `12` | sibling-in-law |
| `13` | step-parent |
| `14` | step-child |
| `15` | step-sibling |

Codes are permanent once assigned; anything new takes the next free number, and
the list can grow indefinitely because nothing depends on its length.

`0` is the fallback: great-grandparents, second cousins, godparents, guardians,
foster relations, in-laws further out than the three listed, and anyone whose
relation the author would rather not spell out. It is also the honest choice when
the author is unsure, since guessing writes a claim about someone else that they
cannot correct.

Spouses are deliberately absent. A partnership is a status about the two people
in it, stated and withdrawn as one thing, and it does not belong here as a second
entry saying the same thing again. The in-laws stay, because a mother-in-law is
family whether or not the marriage that produced her is mentioned anywhere.

Adoption is not separately coded: an adoptive mother is a mother, `1` with `2`.

## Gendered terms

The relation says what the connection is; the optional fifth element says which
gendered word to reach for. `1` is a parent, `1 2` a mother, `1 1` a father.

| Code | |
|------|-|
| `1` | male |
| `2` | female |
| omitted | unspecified |

The numbering is [ISO/IEC 5218](https://www.iso.org/standard/81682.html), which
exists for exactly this reason: it is a language-neutral single digit, defined
because `M` and `F` are derived from English words and a protocol should not
require them. The standard also carries `0` for "not known" and `9` for "not
applicable"; neither is used here, because leaving the element off already says
that, and `0` in an optional slot is the falsy value that a presence check
mistakes for absence. `1` and `2` are safe in every language. No ranking is
implied by the order — that is the standard's own note, and it is worth repeating.

Keeping sex out of the relation code is what makes the list short and the
vocabulary honest. English has no separate word for a feminine cousin, so `9`
simply carries no fifth element from an English client — while a Spanish one
reads `9 2` and renders *prima*, and `7 2` as *tía*. Folding the distinction into
the relation codes instead would mean reserving dead slots for every pair English
happens not to distinguish.

It also lets a client choose its own level. Rendering relations alone is a
complete implementation: an entry marked `2` still reads correctly as "parent" to
a reader that ignores the fifth element, and nothing is lost but the detail that
reader did not want.

## Confirmation

Every entry is one-sided: anyone can name anyone, and nothing in the event proves
a relation. Usually that is fine. A wrong entry is someone's joke, someone's
wishful thinking, or someone who simply has not been named back yet, and none of
those need policing by the format.

A client that wants a firmer signal can look for agreement — the named pubkey's
own `kind:10094` naming the author back with the answering relation. Which fifth
element either side uses is their own business:

    0 ↔ 0     3 ↔ 3     5 ↔ 6      9 ↔ 9      12 ↔ 12    15 ↔ 15
    1 ↔ 2     4 ↔ 4     7 ↔ 8     10 ↔ 11    13 ↔ 14

What to do with that is a display choice: badge the confirmed pairs, sort them
first, or ignore the distinction entirely.

The reverse view is the one to be careful with. An entry on the author's own
profile is the author's business; showing inbound claims on the named person's
profile is letting strangers write on it. Nothing here makes that view cheap to
build — [NIP-01](../nips/01.md) spells a tag filter as `#<single-letter>`, so
there is no query for "who has named this person" — and a client that assembles
it anyway should want agreement first.

Relations do not compose. Two people who each name the same mother are usually
siblings and sometimes are not, so deriving the link publishes a guess about
someone's family.

## Implementation notes

* Tags are arrays of strings and elements past the second carry no fixed meaning,
  so the fourth and fifth slots are ordinary positional values. Read them by
  index, and tolerate tags longer than expected rather than checking length.
* `kin` is a multi-letter tag, and tag filters are spelled `#<single-letter>`, so
  there is no `#kin` to subscribe to and the event does not reach the named
  person's mentions. Nothing about it is addressed to them.
* Look for the tag before testing its value. `Number(tag[3]) || fallback` reads a
  legitimate `0` as missing in JavaScript and Python, and the string `"0"` is
  falsy in Perl and PHP. Presence first, parse second. The fifth element sidesteps
  this by starting at `1`, so `tag[4]` can be presence-checked directly.
* A person may appear twice with different relations — a step-sister who is also
  a sister-in-law, say. Both entries are real; showing only the first loses one.

## Why `kin` and not `p`

`p` marks someone an event is addressed to. That is what relays index it for and
what clients route to notifications, and it is the right tag for a reply, a zap or
a message. The people named here are the event's subject rather than its
audience: it describes them, but nothing in it is written to them.

Family is also the one subject reachable without a protocol. People tell each
other, so the notification buys little.

This is not a privacy measure, and it would be dishonest to present it as one.
The events are public and signed: anyone running a relay or reading the firehose
can assemble "who has named this person", and some will. What the tag decides is
whether that question is answerable incidentally — by any client, on any public
relay, without anyone intending it — or only by someone who set out to answer it.

Confirmation is unaffected, since it is a lookup by author.

## Why not NIP-32 labels

[NIP-32](../nips/32.md) already labels pubkeys, and `kind:1985` with an `L`
namespace would carry roughly this information. Two differences decide it.

`1985` is a regular event, so a list assembled from labels accumulates: removing
one entry means a deletion request rather than replacing the whole statement, and
a reader has to reconcile every label event ever published to know the current
answer. This event is replaceable, so the newest one is the answer.

Label values are free text. `l` of `mother` or `madre` renders as whatever the
author typed, to every reader in every language. A fixed set of codes is the only
part of this design that a translation layer can actually work with.

## Privacy

This event publishes information about people who did not sign it, and often
about children. That makes it different in kind from the rest of a profile: the
subject cannot withdraw an entry, because they do not hold the key that wrote it.

What follows from that:

* An entry is cheap to add and cannot be retracted by the person it names. Bulk
  import from an address book turns a private contact list into a public family
  tree in one action.
* A family nobody published is often reconstructable from other people's lists.
  Assembling it is the interesting part and also the harmful part.
* The moment of adding is the only point at which a client can mention that the
  entry is public, permanent in practice, and about someone who has not agreed to
  it. Afterwards it is already published.
* Pubkeys that have never published anything most likely belong to people who are
  not here by choice.
